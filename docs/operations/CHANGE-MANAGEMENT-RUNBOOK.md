# Change Management Runbook

## Purpose

This runbook governs production changes in SBS AI ITSM. The source of truth is the
tenant-scoped RFC register at `/changes` and the API under `/api/v1/changes`.

The process is designed to prevent four common failure modes:

- unassessed production work;
- self-approval of high-impact work;
- overlapping maintenance on the same asset;
- completion without validation or a recorded rollback outcome.

## Roles and separation of duties

| Capability | Organization admin | IT manager | IT agent | Security officer |
|---|---:|---:|---:|---:|
| Read register and history | Yes | Yes | Yes | Yes |
| Create/update/submit RFC | Yes | Yes | Yes | No |
| CAB/ECAB decision | Yes | Yes | No | No |
| Schedule window | Yes | Yes | No | No |
| Execute/close/rollback | Yes | Yes | Yes | No |

SaaS Root has every capability. A requester cannot access the internal change register.
The RFC requester cannot approve their own change even if another assigned role grants
`changes.approve`.

## Lifecycle

```text
DRAFT -> ASSESSMENT -> APPROVAL_PENDING -> APPROVED -> SCHEDULED
                                                        |
                                                        v
                                                  IMPLEMENTING
                                                   /    |    \
                                             REVIEW   FAILED  ROLLED_BACK
                                               |        |
                                          COMPLETED  ROLLED_BACK
```

`STANDARD` changes that remain low/medium risk and require no outage are pre-authorized:
`ASSESSMENT -> APPROVED`. They still require complete implementation, test, rollback and
validation plans. `NORMAL` and `EMERGENCY` changes require an explicit CAB/ECAB decision.

## Create and assess an RFC

1. Create a draft and name the affected service.
2. Link every known affected asset and originating incident/request.
3. Record business justification, implementation, testing, rollback and validation plans.
4. Declare impact, likelihood, outage requirement and expected outage duration.
5. Submit the draft for assessment.

Risk is calculated by the backend. The score combines impact, likelihood, outage,
emergency type and affected-asset count. Operators cannot directly override the resulting
risk level or whether CAB is required.

If a Standard Change is rejected at submission, convert it to Normal or reduce its scope.
Never split one risky change into artificial Standard Changes to bypass approval.

## CAB / ECAB decision

1. Confirm the assessment contains all five control plans.
2. Review service impact, linked assets/incidents, outage and rollback feasibility.
3. Add a decision comment that states the accepted risk and constraints.
4. Approve or reject. Rejected work returns to an editable state and must be resubmitted.

Every decision is stored as an immutable `change_approvals` record and as a chained audit
event. Approval is invalid if the approver is the RFC requester.

## Schedule the implementation window

Only an approved RFC can be scheduled. Both start and end are mandatory and the end must
be later than the start.

Scheduling acquires transaction-scoped advisory locks on PostgreSQL for all linked assets,
then checks existing `SCHEDULED` and `IMPLEMENTING` changes. An overlap returns HTTP 409
with the conflicting change number and asset tag. Resolve the collision by selecting a new
window or formally cancelling/rescheduling the other RFC.

Do not remove a genuinely affected asset merely to bypass the collision guard.

## Execute, validate and close

1. At the approved window, move `SCHEDULED -> IMPLEMENTING`.
2. Follow the recorded implementation plan and collect validation evidence.
3. If implementation succeeds, move to `REVIEW`.
4. Record the post-implementation review and close as `COMPLETED`.
5. If validation fails, record the failure reason and execute the rollback plan.
6. Record the rollback result; the terminal status is `ROLLED_BACK`.

Closing, failure, rollback and cancellation require an operator comment. Actual start/end
timestamps are generated by the backend.

## Concurrent update handling

Every RFC has a monotonically increasing `version`. All updates, decisions and transitions
must send `expected_version`. HTTP 409 means another operator changed the RFC first:

1. reload the RFC;
2. review the new history entry;
3. repeat the action against the current version if it remains valid.

Never automate blind retries of state transitions.

## Audit and incident response

Business history is stored in `change_history`; security evidence is written to the
tenant's tamper-evident `audit_logs` chain. Relevant audit actions start with `changes.`.

For a disputed or failed change:

1. preserve the RFC, approval and history records;
2. export the related audit events using the security console;
3. link/create the production incident;
4. complete rollback before starting a replacement RFC;
5. record corrective actions in the post-implementation review.

## Deployment and verification

```bash
cd backend
alembic upgrade head
alembic current
pytest tests/test_change_management.py tests/test_change_migration.py

cd ../frontend
npm run build
```

Expected Alembic head: `20260720_0026`.

After deployment, verify:

- `/api/v1/changes/summary` returns HTTP 200 for an IT manager;
- a requester receives HTTP 403 for `/api/v1/changes`;
- a Normal Change cannot be self-approved;
- overlapping windows on the same asset return HTTP 409;
- the RFC history and Security Audit both contain the completed test flow.
