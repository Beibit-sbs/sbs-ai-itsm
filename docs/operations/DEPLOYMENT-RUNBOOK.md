# DEPLOYMENT RUNBOOK

## Prerequisites
- Docker and Docker Compose are installed.
- `.env.production` is configured locally and not tracked by git.
- Production secrets are unique and rotated (`JWT_SECRET_KEY`,
  `CREDENTIAL_ENCRYPTION_KEY`, database, Redis, bootstrap root and metrics
  token).
- Public TLS termination/reverse proxy is configured; the bundled frontend binds to loopback by default.
- Docker secret files are stored in a protected directory outside git.
- If OIDC is enabled, the provider-issued client secret has replaced the disabled value in
  `secrets/oidc_client_secret` and the identity runbook has been completed.
- Backups are enabled and tested.

## First Deploy
1. Prepare env:
   - `cp .env.production.example .env.production`
   - Keep `APP_ENV_FILE=.env.production`, set the public HTTPS origin, and
     change `SECRETS_DIR` from `./secrets.example` to `./secrets`.
   - Choose an unused `EDGE_SUBNET`; keep `TLS_PROXY_CIDR` equal to the exact
     `EDGE_GATEWAY` `/32`, `FORWARDED_ALLOW_IPS` equal to
     `FRONTEND_EDGE_IP`, and list the public hostname plus `backend` in
     `TRUSTED_HOSTS`. Follow `EDGE-TRUST-BOUNDARY-RUNBOOK.md`.
2. Generate first-deploy secrets:
   - `python3 scripts/init-production-secrets.py --directory secrets --with-bootstrap-password`
   - Store an approved backup in the organization secret manager.
3. Validate env and secrets:
   - `bash scripts/check-production-env.sh`
   - On Windows or any host without Bash:
     `python scripts/check-production-env.py --env-file .env.production`
   - Run `python scripts/validate_edge_security.py`.
4. Validate compose:
   - `docker compose -f docker-compose.prod.yml --env-file .env.production config --quiet`
5. Start the first-deploy stack:
   - `docker compose --project-name sbs-itsm-production -f docker-compose.prod.yml -f docker-compose.bootstrap.yml --env-file .env.production up -d --build`
   - The one-shot `migrate` service must complete successfully before backend/worker start.
6. Verify runtime:
   - `python3 scripts/smoke-production.py --env-file .env.production --base-url https://itsm.example.com`
7. After first login, rotate the SaaS Root password, remove `BOOTSTRAP_ROOT_EMAIL`, archive/delete `secrets/bootstrap_root_password`, and relaunch using only `docker-compose.prod.yml`.
   - The non-interactive rotation utility can be used before removing the
     bootstrap overlay:
     `python3 scripts/rotate-bootstrap-root.py --env-file .env.production --base-url https://itsm.example.com`
   - Move the resulting root credential to the approved secret manager.

If secret files were generated by an older Windows workflow, normalize their
line endings before the first launch:
`python scripts/init-production-secrets.py --directory secrets --normalize-existing`.

## Update Deploy
1. Pull latest code.
2. Run pre-update backup:
   - `bash scripts/backup-db.sh`
3. Build, migrate and restart:
   - `docker compose --project-name sbs-itsm-production -f docker-compose.prod.yml --env-file .env.production up -d --build`
4. Confirm `migrate` exited with code 0 and backend/frontend are healthy.
5. Post-deploy checks:
   - `python3 scripts/smoke-production.py --env-file .env.production --base-url https://itsm.example.com`

## Migration Procedure
- Compose runs an explicit one-shot `alembic upgrade head` migration before application services.
- Verify migration state:
  - `make db-current`
  - `make db-head`
- Do not rely on startup DDL in production.

## Horizontal Backend Scaling
- Start multiple API replicas with `docker compose -f docker-compose.prod.yml --env-file .env.production up -d --scale backend=2`.
- Nginx resolves the backend service dynamically.
- Redis Pub/Sub distributes dashboard events and a distributed lease prevents duplicate polling.
- Do not scale the worker service until a workload-specific concurrency/load test has been approved.

## Backup Before Update
- Always run:
  - `bash scripts/backup-db.sh`
  - `bash scripts/backup-data.sh`

## Rollback Procedure
1. Roll application images to previous known-good tag/commit.
2. Restart services with previous image set.
3. If schema rollback is required, apply controlled downgrade plan only after approval.
4. If needed, use DB restore runbook.

## Enterprise identity

- Follow `docs/operations/ENTERPRISE-IDENTITY-RUNBOOK.md` before enabling OIDC.
- Roll out pre-linked users first; do not enable auto-provisioning during the initial cutover.
- Preserve and test a local break-glass root account before changing IdP policy.

## Microsoft 365 email channel

- Follow `docs/operations/PRODUCTION-EMAIL-CHANNEL-RUNBOOK.md`.
- Set `EMAIL_PUBLIC_BASE_URL` to the public HTTPS application origin before
  creating a Graph webhook subscription.
- Back up and restore the `email_attachment_data` volume with PostgreSQL.
- Keep `credential_encryption_key` in the approved secret manager. Losing it
  makes saved Graph credentials and delta checkpoints unrecoverable.
- Configure ClamAV before allowing automatic release of inbound attachments.

## Restore Procedure
- See `docs/operations/BACKUP-RESTORE-RUNBOOK.md`.

## Smoke-Check After Deploy
- Run `scripts/smoke-production.py` against the public HTTPS URL.
- Configure a dedicated least-privilege `SMOKE_EMAIL` and `SMOKE_PASSWORD` to include login/me/logout checks.
- The script also verifies readiness (Postgres, Redis, Alembic and runtime), frontend, anonymous access denial and authenticated Prometheus metrics.
- Grafana health is checked through its loopback production port.

## Troubleshooting
- Containers unhealthy: `docker compose ps`, `make logs-backend`, `make logs-frontend`.
- Migration mismatch: `make db-current`, `make db-head`.
- Startup failures: inspect backend health and DB/Redis connectivity.
